  <what-built>N/A — owner actions in Hostinger hPanel and Cloudflare SSL/TLS panel.</what-built>

  <action>
    **Owner performs both steps:**

    **Step A — Swap nameservers at Hostinger:**
    1. hPanel → Domains → Domain Portfolio → click unth.ai → Manage
    2. Find "Nameservers" or "DNS / Nameservers" section
    3. Select "Change to Custom nameservers"
    4. Enter the two Cloudflare nameservers from Task 1 (e.g. `alice.ns.cloudflare.com` and `bob.ns.cloudflare.com`)
    5. Save / Confirm
    6. Note the time — this is "NS swap time"

    **Why the 24h wait from Plan 01 matters:** NS records are now changing to CF's servers. Old resolvers cached the TTL=300 we set in Plan 01, so they re-check every 5 minutes and will pick up the new NS quickly. Full propagation is typically 5-30 minutes with TTL=300 (vs 4-24h with default TTLs).

    **Step B — Set SSL mode to Full in Cloudflare:**
    1. Cloudflare Dashboard → unth.ai → SSL/TLS → Overview
    2. Under "Your SSL/TLS encryption mode", select: **Full**
       (NOT Flexible — Flexible sends HTTP to Hostinger origin, weakening security)
       (Full (Strict) also works if Hostinger's shared cert is CA-signed, which it is)
    3. Save

    **Rationale:** Full mode means CF connects to Hostinger's origin over HTTPS. Hostinger provides a valid shared SSL cert at 145.223.108.64, so Full mode works correctly. Flexible mode would send plaintext HTTP to the origin — visible on the internal network and incorrect from a security standpoint.
  </action>

  <how-to-verify>

    # Check A record — should show Cloudflare IP, NOT 145.223.108.64

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Hostinger hPanel → Cloudflare NS | Owner authenticates at Hostinger to authorize the NS swap |
| Cloudflare edge → Hostinger origin | SSL Full mode ensures encrypted connection; Flexible would be plaintext |
| CF DNS zone (orange vs grey cloud) | Orange = CF proxies + can inject headers; Grey = DNS passthrough only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | Denial of Service | mail.unth.ai proxied accidentally (orange cloud) | mitigate | Task 1 explicitly requires mail.unth.ai to be grey cloud. Task 3 verifies mail.unth.ai still responds post-swap. |
| T-02-02 | Spoofing | SSL mode set to Flexible — CF decrypts and re-sends HTTP to origin | mitigate | Task 2 explicitly sets SSL mode to Full. Pitfall 5 from RESEARCH.md documents the risk. |
| T-02-03 | Denial of Service | DNS records missing after CF import (Pitfall 2) | mitigate | Task 1 requires manual comparison of CF imported records against the pre-flight baseline before clicking Continue. |
| T-02-04 | Denial of Service | NS swap before TTL propagation causes long outage window | mitigate | Plan 01 lowered TTL to 300s and required 24h wait; this plan's depends_on: [01-01] enforces sequencing. |
</threat_model>
